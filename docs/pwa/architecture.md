# PWA architecture

Two installable apps, one per origin. Nothing is shared between them at run time.

| | Greenscape Admin | Greenscape Employee |
|---|---|---|
| Next.js app | `apps/admin` | `apps/employee` |
| Production origin | `https://admin.greenscapelandscapingph.com` | `https://employee.greenscapelandscapingph.com` |
| Manifest | `/manifest.webmanifest` (`app/manifest.ts`) | same path, its own content |
| Service worker | `/sw.js`, scope `/` | `/sw.js`, scope `/` |
| Cache | `gs-admin-<build>` | `gs-employee-<build>` |
| Push subscriptions | stored with `app = admin` | stored with `app = employee` |

The customer site (`apps/web`) is not an installable app. It keeps its push-only service worker.

## What was there before (audit, 2026-11-14)

- Admin and Employee were already separate Next.js 16 apps with their own Dockerfiles, proxies (`proxy.ts`, nonce CSP) and Supabase sessions.
- Web Push (VAPID), the in-app notification stream, sounds and a push-only service worker already existed (`docs/notifications.md`). They are reused, not replaced.
- Missing: manifests, an offline screen, install controls, per-app icons (all three apps shared one "G" PNG), safe-area handling.

No PWA library was added. Next's built-in `app/manifest.ts` and a hand-written worker of about 60 lines cover it; a plugin would have brought runtime caching the apps must not have.

## Where the code is

| File | What |
|---|---|
| `packages/ui/src/pwa/app.ts` | Per-app name, colours, icon paths; `manifestFor()`; `offlineResponse()` |
| `packages/ui/src/notifications/sw.ts` | The worker source: offline fallback + push, parameterised by app |
| `packages/ui/src/pwa/client.tsx` | `PwaRegistration`, `InstallApp`, `OfflineBanner`, `useOnline` |
| `apps/*/app/manifest.ts`, `app/offline/route.ts`, `app/sw.js/route.ts` | Three-line route files that pick the app |
| `apps/*/public/icons/` | App icons (generated by `scripts/brand-assets.mjs`) |
| `tests/e2e/pwa.spec.ts` | Playwright checks |

`PwaRegistration` and `OfflineBanner` sit in each root layout. `InstallApp` is on Employee → Profile and Admin → Settings.

## Request flow

```
page navigation ──► service worker ──► network ──► page (never stored)
                          │ network failed
                          └──► cached /offline screen (public, no data)

/icons/*  ──► network, else the copy installed with the worker
everything else (scripts, styles, API, server actions) ──► browser as usual, worker not involved
```

## Deployment (Docker, Dokploy)

No new service, environment variable or build argument. What production needs:

| Requirement | Where |
|---|---|
| HTTPS on both origins | The TLS proxy in front of the apps (already required). Without it browsers refuse the worker and installation. |
| `public/` in the image | `apps/admin/Dockerfile` and `apps/employee/Dockerfile` now copy `apps/<app>/public` next to the standalone server (the icons live there). |
| `/sw.js`, `/manifest.webmanifest`, `/offline`, `/icons/*` reach the app unchanged | Nothing to configure in Dokploy/Traefik: they are ordinary paths of the app. Do not add a CDN rule that caches `/sw.js`. |
| Content types | Set by the app: `text/javascript`, `application/manifest+json`, `text/html`, `image/png`. |
| Health check | Unchanged (`/api/health`). |
| Push | `VAPID_*` on the API, and both origins in `CORS_ORIGINS`, as before (`docs/deployment/subdomains.md`). |

After a deployment, open browsers pick up the new worker on their next visit; it replaces the previous cache by itself. Nothing has to be purged.
