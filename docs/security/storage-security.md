# Supabase Storage security

## Buckets (`packages/storage/src/index.ts`, created by `pnpm storage:setup`)
| Bucket | Public | Types | Size | Holds |
|---|---|---|---|---|
| `public-media` | yes (read) | JPEG, PNG, WebP, AVIF, GIF | 15 MB | CMS photos, product images, gallery |
| `private-docs` | **no** | JPEG, PNG, WebP, HEIC, PDF | 10 MB | Quote attachments from customers |
| `employee-private` | **no** | JPEG, PNG, WebP, PDF | 10 MB | Reserved for employee documents (unused: clock-in photos are off, D6) |

The type and size limits are enforced by Supabase on upload, in addition to the API's checks.

## Access model: deny by default
- There are **no Storage row-level security policies** for the `anon` or `authenticated` roles, so browser keys can't read, list, write or delete in any bucket. Public buckets are readable through their public URLs only.
- Writes happen through **signed upload URLs** that the API issues for one path at a time, after a permission or rate-limit check. Reads of private files happen through **signed URLs of 300 seconds**, issued by the API to staff with `quotations.read`.
- File names are generated by the server (`<uuid>.<ext>` under a dated or pending prefix); client file names are never used as paths.

## Upload pipeline
1. **Reserve**: the client sends the declared type and size; the API checks both against an allow-list, creates a `MediaAsset` row and returns a one-time signed upload URL.
2. **Upload**: the browser puts the bytes straight to Storage. Supabase enforces the bucket's type and size limits.
3. **Verify**:
   - CMS images: the API downloads the object, checks the **magic bytes** match the declared type, and **fully decodes** it with sharp (16-px blur). A mismatched or corrupt file is deleted with its row.
   - Quote attachments: the API inspects the stored object (size and sniffed type) before the quote can reference it.
4. **Sweep**: unclaimed uploads (attachments never used in a quote) are removed by `pnpm media:sweep`.
5. **Delete**: CMS images are refused while any content still references them. Deletions are audited.

## Image processing safeguards
- sharp runs with `animated: false` and only resizes to 16 px for the placeholder.
- `next/image` optimises only configured remote patterns. Private addresses are refused unless Supabase itself is local (dev/CI); this is the SSRF guard.

## Malware scanning (L-6, accepted)
Attachments aren't scanned. Compensating controls:
- only images and PDFs are accepted, checked by magic bytes;
- the bucket is private;
- staff open files through 5-minute signed URLs as downloads;
- the admin never renders them inline.

Recommended if attachment volume grows: a ClamAV step between "uploaded" and "claimed" (a Supabase webhook to a scanning function), quarantining on detection.

## Verification
- `tests/integration/security.test.ts`, "storage": the anon key and a signed-in customer can't download or list a private document, and its public URL doesn't work; a 60-second signed URL from the API's service role reads it.
- `cms.test.ts`: mislabelled and corrupt images are refused and removed.
- e2e quote flow: upload, reference, staff download.
